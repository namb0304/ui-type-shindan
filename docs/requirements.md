# UIタイプ診断 要件定義書

2026年10月20日 · @南保俊輔

最終更新 2026年10月23日：方針を3層構成に見直し、第2部「定番UIキット」（10問）を追加。4つめの軸を「文字」から「見出し」に変更。16タイプの呼び方を「お店」から「場所」に変更。

## 1. 概要

2択の質問に答えるだけで、自分の好きなUIが「**どんな場所の雰囲気か**」と「**どんな部品でできているか**」の両方で分かり、そのままAIに渡せる設計図が手に入るWebサービス。


| 項目      | 内容                                                        |
| ------- | --------------------------------------------------------- |
| タイトル    | 画面上の表示名「あなたのデザインの好み、場所でいうと？」（リポジトリ名は `ui-type-shindan` のまま。「MBTI」は商標のため名称に使わない） |
| 目的      | UIの好みは人によって違うことを体験してもらう。自分の好みを言語化し、AIでのUI制作に使える形で持ち帰ってもらう。あわせて、UI部品に名前があることを知ってもらう |
| ユーザー    | 同年代の友人・先輩・後輩（主にスマホ）。評価者として先生も閲覧する                         |
| 解決したい課題 | 好きなUIを言葉で説明できない／AIにデザインを頼むとありきたりなUIになる／UI部品の名前を知らないので、AIにも人にも頼みようがない |
| 位置づけ    | エンタメ診断。科学的な根拠はないことを明記する                                   |
| 課題      | 専門デプロイメントコースⅢ 中間課題（個人）。締切 2026-10-29 0:00（実質 10/28 中）     |


### 3つの層

このサービスは3つの層でできている。どれか1つではなく、3つ揃って初めて「AIに渡せる自分の設計図」になる。


| 層  | 名前                       | 中身                                                 | 問数       |
| -- | ------------------------ | -------------------------------------------------- | -------- |
| 入口 | あなたのデザインの好み、場所でいうと？      | 雰囲気の好みを4軸で測り、16の「場所」のどれかに当てはめる                      | 12問（第1部） |
| 中身 | あなたの定番UIキット              | よく見るUI部品・レイアウト・動きの好みを、「一貫して使える自分の定番」としてまとめる         | 10問（第2部） |
| 出口 | AIに渡せる、あなたのデザインの設計図      | 第1部（雰囲気）と第2部（部品・動き）の両方を、AIにそのまま貼れる文章にする             | —        |


### 「お店」から「場所」へ

16タイプは「お店」ではなく「**場所・シチュエーション**」として扱う。タイプの呼び名（§12）と写真はこれまでのものをそのまま使い、**画面に出す言葉だけを「場所」に置き換える**。

- 「気が合うお店」→「気が合う場所」
- 「たぶん落ち着かないお店」→「たぶん落ち着かない場所」
- 「お店の相性」→「場所の相性」

「市役所の窓口」「空港の出発ロビー」のように、もともと店ではないタイプが多いため。

### 非機能要件

- 初回表示が軽いこと。外部サービスからの読み込みはフォント（Google Fonts）だけ
- 結果ページのファーストビューにだけ、同一オリジンの写真を1枚読み込む（`public/images/shops/{タイプコード}.webp`・1枚150KBまで）。診断が終わってから、結果に出たタイプの1枚だけを読み込む。写真が無い・読み込めない場合もテーマ色のグラデーションだけで成立させる
- 写真の元のPNGは `design/shops-src/` に置く（`public/` の中身はそのままデプロイされるため、`public/` には WebP だけを置く）
- 個人情報は一切集めない
- 主要ブラウザ（iOS Safari / Android Chrome / PC Chrome）で動く

## 4. 診断の構成と判定ロジック

診断は2部構成にする。**タイプコードを決めるのは第1部だけ**で、第2部は判定に使わない。


| 部   | 名前        | 問数  | 聞くこと              | 判定への影響      |
| --- | --------- | --- | ----------------- | ----------- |
| 第1部 | 雰囲気の4軸    | 12問 | 情報量・装飾・トーン・見出し    | 16タイプを決める   |
| 第2部 | 定番UIキット   | 10問 | よく使うUI部品・レイアウト・動き | 使わない（結果に並べる） |


間にひと休みの画面を1枚挟む（§5）。

### 4.1 第1部：雰囲気の4軸（12問）

4つの軸を3問ずつ測り、多く選んだ側の文字を並べて4文字のタイプコード（例：`ARCG`）にする。1つの軸が3問なので、引き分けは起きない。

#### 4つの軸


| 順   | 軸   | 左側（文字）         | 右側（文字）       |
| --- | --- | -------------- | ------------ |
| 1   | 情報量 | ギッシリ Dense（D）  | ユッタリ Airy（A） |
| 2   | 装飾  | フラット Flat（F）   | リッチ Rich（R）  |
| 3   | トーン | クール Cool（C）    | ポップ Pop（P）   |
| 4   | 見出し | ゴシック Gothic（G） | 明朝 Mincho（M） |


#### 4つめの軸は「見出しの雰囲気」で測る

4つめの軸の名前を「文字」から「**見出し**」に変える。

実際のUIで、本文に明朝体を使うことはほとんどない。画面で長い文章を読むならゴシック体のほうが読みやすいからで、本文まで明朝にすると「好み」ではなく「読みにくさ」を選ばせることになる。そこでこの軸は、**見出しだけ**を変えて測る。


| 文字      | 見出し                   | 本文                   |
| ------- | --------------------- | -------------------- |
| G（ゴシック） | ゴシック体（Noto Sans JP）   | ゴシック体（Noto Sans JP）  |
| M（明朝）   | 明朝体（Noto Serif JP）    | ゴシック体（Noto Sans JP）  |


- CSS変数を `--font-family-heading` と `--font-family-body` の2つに分ける（§6）
- 説明文とAI向けの設計図（§7）の文言も、これに合わせて書き換える
- 題材（Q4 ニュース記事の見出し／Q8 プロフィールカード／Q12 イベント告知）はそのまま使える。3つとも見出しと本文の両方を持っているので、見出しだけが変わる差として成立する
- タイプコードの文字（G／M）は変えない。これまでの結果・共有URL・写真がそのまま使える

#### 質問設計の原則

- 比べる2つのUIは、**測る軸だけが違い、他の3軸はニュートラル値で同じ**にする（視力検査方式）
- 問題ごとに題材を変え、場面が偏らないようにする
- 同じ軸の問題が連続しないよう、軸1→2→3→4の順で3周させる
- 選択肢A/Bの左右は問題ごとにランダムに入れ替え、位置による偏りを防ぐ
- 質問文は全問共通で「どっちが好き？」。軸の名前は回答中には見せない（先入観を防ぐ）


| 問   | 軸   | 題材         |
| --- | --- | ---------- |
| Q1  | 情報量 | カフェのメニュー   |
| Q2  | 装飾  | 音楽プレイヤー    |
| Q3  | トーン | 天気アプリ      |
| Q4  | 見出し | ニュース記事の見出し |
| Q5  | 情報量 | ECの商品カード   |
| Q6  | 装飾  | ログイン画面     |
| Q7  | トーン | ToDoリスト    |
| Q8  | 見出し | プロフィールカード  |
| Q9  | 情報量 | 大学の時間割     |
| Q10 | 装飾  | 通知一覧       |
| Q11 | トーン | SNSの投稿     |
| Q12 | 見出し | イベント告知     |


#### 回答の選択肢

2つのUIの差が分からない人に無理やり選ばせると回答が実質ランダムになり、判定が濁る。そのため2択の下に「どっちも同じに見える」を小さく置く（2択と同じ大きさのボタンにはしない）。


| 回答           | 右側に寄せる点数 |
| ------------ | -------- |
| 左側を選ぶ        | 0        |
| どっちも同じに見える   | 0.5      |
| 右側を選ぶ        | 1        |


#### 判定と割合

- 各軸の3問について、上の点数を合計する（0〜3）
- 小数を避けるため、内部では**合計を2倍した整数**（0〜6）で持つ
- 右側の割合 = 合計 ÷ 3 ＝ 2倍した値 ÷ 6（0% / 17% / 33% / 50% / 67% / 83% / 100%）。左側の割合 = 100% − 右側
- 割合が **50%より大きければ**右側の文字、**50%以下なら**左側の文字をタイプコードに使う（ちょうど50%は左側）
- 割合はデザイントークンの値の決定にも使う（同じタイプでも少しずつ違うUIになる）
- **テーマのプリセット切り替えも、タイプコードとまったく同じ境界・同じ比較を使う。** 片方だけ「50%以上」にすると、ちょうど50%のときにタイプコードと見た目が食い違う
- 16タイプそれぞれに、呼び名（§12）と解説文を用意する


| 2倍した値 | 0  | 1   | 2   | 3   | 4   | 5   | 6    |
| ----- | -- | --- | --- | --- | --- | --- | ---- |
| 右側の割合 | 0% | 17% | 33% | 50% | 67% | 83% | 100% |
| 使う文字  | 左側 | 左側  | 左側  | 左側  | 右側  | 右側  | 右側   |


### 4.2 第2部：定番UIキット（10問）

第1部が「雰囲気」なら、第2部は「**部品**」。よく見るUI部品・レイアウト・動きについて、どちらが好きかを10問聞き、「一貫して使える自分の定番」としてまとめて結果に出す。

- 回答は2択＋「どっちでもいい」。第1部と同じ3択にそろえる
- **第2部の回答は16タイプの判定には使わない。** タイプコードは第1部の12問だけで決まる
- 各問は、**実際に動くデモを2つ見比べて選ぶ**（トーストが本当に出て消える、ボトムシートが本当にせり上がる）。説明文を読んで選ぶのではなく、動きを見て選べるようにする
- デモは**ニュートラルのテーマ**（§6）で表示する。ここで測るのは部品の好みであって、色や余白の好みではないため

#### 質問と、選ぶもの

部品には必ず**名前と一言の説明**を付ける。UIの名前を知らない人が「これ、そういう名前なんだ」と分かること自体を、このサービスの価値のひとつにする。


| 問   | 分類       | 聞くこと      | A                                  | B                                |
| --- | -------- | --------- | ---------------------------------- | -------------------------------- |
| K1  | レイアウト    | メニューの出し方  | **ハンバーガーメニュー**：三本線を押すと、隠れていたメニューが出てくる | **ボトムナビ**：画面の下にいつも並んでいる、行き先のボタン   |
| K2  | レイアウト    | 一覧の見せ方    | **リスト**：1行ずつ縦に並べる。一度にたくさん見渡せる       | **カード**：1件を四角い面で見せる。写真や見出しが目立つ    |
| K3  | レイアウト    | 続きの見せ方    | **無限スクロール**：下まで行くと、次が勝手に読み込まれる      | **「もっと見る」ボタン**：押したぶんだけ続きが出る      |
| K4  | コンポーネント  | お知らせの出し方  | **トースト**：画面の端に一瞬出て、自分で消える           | **バナー**：画面の上に出たまま残り、自分で閉じる        |
| K5  | コンポーネント  | 確認・選択パネル  | **モーダル**：画面の真ん中に重なって出る窓             | **ボトムシート**：画面の下からせり上がってくる板       |
| K6  | コンポーネント  | 読み込み中の見せ方 | **スケルトンスクリーン**：中身の形を先に灰色で出して待たせる    | **スピナー**：くるくる回る印で待たせる            |
| K7  | コンポーネント  | 切り替えの形    | **セグメントコントロール**：横に並んだボタンを押して切り替える   | **タブ**：見出しが並び、その下の中身が入れ替わる       |
| K8  | コンポーネント  | 入力ミスの伝え方  | **その場で出す**：入力欄のすぐ下に、打った直後に出す        | **まとめて出す**：送信ボタンを押してから、上にまとめて出す  |
| K9  | アニメーション  | 動きの速さ     | **きびきび**：0.15秒ほどで終わる               | **ふんわり**：0.35秒ほどかけて動く            |
| K10 | アニメーション  | 画面の切り替わり  | **スライド**：横に滑って入れ替わる                | **フェード**：すうっと薄れて入れ替わる           |


#### 「どっちでもいい」を選んだとき

| 使う場所            | 扱い                        |
| --------------- | ------------------------- |
| AI向けの設計図（§7）    | 書かない（こだわらない項目として外す）       |
| 結果ページのてんこ盛り化    | Aを既定値として使う                |
| 「定番UIキット」の一覧    | 「どちらでも」と表示する              |


#### 動きが苦手な人への配慮

`prefers-reduced-motion: reduce` のときは、**動きを止めた状態でも違いが分かるようにする**。動かないと差が見えない作りにはしない。

- K4 トースト／バナー：出入りのアニメーションを消し、出る位置と形の違いで見せる
- K5 モーダル／ボトムシート：せり上がりを消し、出る位置の違いで見せる
- K6 スケルトン／スピナー：明滅と回転を止め、形の違いで見せる
- K9・K10：動きそのものが問題なので違いを出せない。「この設定では違いが出ません」と伝えたうえで、「どっちでもいい」を既定にする

#### ひと休み

第1部（12問）と第2部（10問）の間に、ひと休みの画面を1枚挟む（§5）。22問を続けて出すと途中で飽きるため。文面の例：「前半おわり！ここからは、よく見るUIの好みを聞きます」。


## 5. 画面構成とUI

1枚のHTMLの中で画面を切り替えるSPA（シングルページアプリケーション）構成にする。ページを読み直さないので、回答の状態を保ちやすい。

**ui-craftというskill使いながら進める**

1. **トップ**：サービス名、ひとこと説明、3つの層（§1）が伝わる説明、「約4分・22問」、エンタメであることの注記、開始ボタン
2. **第1部の質問**（×12）：進捗バー（例：5/12）、「どっちが好き？」、2つのUIプレビュー（スマホでは上下に並べ、PCでは左右に並べる）、戻るボタン。タップしたら次の問題へ進む
3. **ひと休み**：「前半おわり！ここからは、よく見るUIの好みを聞きます」と、残りの問数。続けるボタン。1枚だけの軽い画面にする
4. **第2部の質問**（×10）：進捗バー（例：3/10）、聞くこと（例：「お知らせの出し方」）、動くデモ2つ、戻るボタン
   - デモは**触って試せる**ようにする（押すとトーストが出る、ボトムシートがせり上がる）。そのため、第1部のように「カード全体がタップ領域」にはできない
   - デモの下に「**これにする**」ボタンを別に置き、選択と操作を分ける
   - 名前と一言の説明（§4.2）を、デモのすぐ上に出す。回答しながら名前を覚えられるようにする
   - 2択の下に「どっちでもいい」を小さく置く（第1部の「どっちも同じに見える」と同じ扱い）
5. **結果**：ページ全体が、そのタイプのテーマ（CSS変数）に切り替わる。上から順に以下を並べる
   1. ファーストビュー：同じ写真を2回使う
      - **背景**：大きくぼかして画面全体に敷き、テーマ色を重ねる。左右に空白を作らない
      - **前景**：縦長の枠にくっきり出す（切らずに見せる）
      - 同じURLなので、読み込みは1枚ぶんで済む
      - **スマホ**：上に写真（高さは画面の半分〜6割）、下に文字。スクロールしなくても店名とタイプコードが見える
      - **PC（幅900px以上）**：左に縦長の写真、右に文字の2カラム。文字は写真に対して上下中央にそろえる
      - 文字はぼかした背景の上に乗るので、その下にテーマ色のパネル（`--panel-scrim`）を敷く。背後が真っ黒な写真でも 4.5:1 を保てる濃さ（0.94）を下限とする
      - 加工の強さはCSS変数にまとめる：`--photo-opacity` / `--photo-tint`（くっきり写真）、`--hero-bg-blur` / `--hero-bg-opacity` / `--hero-bg-tint`（ぼかし背景）、`--panel-scrim`（文字パネル）
      - 発表演出：「あなたのデザインの好みは……」→ 一拍おいて店名を表示（1.5秒以内。`prefers-reduced-motion` のときは演出なしで即表示）
      - 店名の下に、「タイプ」とタイプコード → タイプの説明文（4軸から自動生成・大きめ）→ ひとこと（§12・オチなので小さく）の順で並べる
      - 写真が無い・読み込めないタイプは、テーマ色のグラデーションだけで成立させる
   4. UIあるある：軸ごとに1つずつ、計4つ（左右8パターン＋ちょうど50%のとき用の4パターン）
   5. 4軸の割合バー（各ラベルにタイプコードの文字を小さく添える）
   6. あなた専用UIのプレビュー（質問で使った部品のうち3つを、その人の値で再描画）
   7. **あなたの定番UIキット**（第2部の結果・新規）
      - 10問ぶんを、分類（レイアウト／コンポーネント／アニメーション）ごとに並べる
      - 1項目につき、**部品の名前・一言の説明・実際に動く見本**の3つを出す
      - 見本はその人のテーマ（CSS変数）で描く。結果ページ全体と同じ見た目になる
      - 「どっちでもいい」を選んだ項目は「どちらでも」と表示する（§4.2）
   8. 場所の相性
      - 気が合う場所：割合が最も50%に近い軸の文字を1つだけ反転したタイプ（同じ近さなら軸の順で先のもの）
      - たぶん落ち着かない場所：4文字すべてを反転したタイプ
   9. AIに渡せる設計図（コピーボタン付き）
   10. エンタメである注記、もう一度診断する
   11. デザイントークンのコピー（P1）、結果をシェア（P1）

   演出は「看板が灯る」の一度きりに絞る。ページ全体がその人のテーマになっていること自体が見せ場なので、それ以外の装飾は足さない。
6. **タイプ一覧**（P2）：16タイプのカードを並べる

### 結果ページのてんこ盛り化

結果ページを「選んだ部品の見本市」にする。第2部で選んだ部品を、**結果ページ自体の作りに使う**。読むだけのページではなく、自分の定番で組まれたページを触ることになる。


| 第2部の問          | 結果ページのどこに使うか                           |
| -------------- | -------------------------------------- |
| K4 お知らせ        | 設計図やトークンをコピーしたときの「コピーしました」が、トースト／バナーになる |
| K6 読み込み中       | 結果を出す前の待ち時間が、スケルトン／スピナーになる             |
| K9 動きの速さ       | ページ全体のアニメーションの長さが変わる                   |
| K10 画面の切り替わり   | 画面が切り替わるときの出方が、スライド／フェードになる            |
| K5 確認・選択パネル    | 「もう一度診断する」の確認が、モーダル／ボトムシートで出る          |
| K2 一覧の見せ方      | 「定番UIキット」の並べ方が、リスト／カードになる              |
| K7 切り替え        | 設計図とトークンの切り替えが、セグメントコントロール／タブになる       |


- **自然に使える場所だけでよい。** 無理に10問すべてを結果ページに反映させようとしない
- K1（メニュー）・K3（続きの見せ方）・K8（入力ミス）は、結果ページに自然な置き場所がないので、見本を並べるだけにする
- 最低1か所（K4 コピー時のお知らせ）はP0。残りはP1とし、間に合わなければ見本だけにする
- てんこ盛り化しても、結果ページが読めなくなってはいけない。コントラスト比4.5:1と、幅375pxで横スクロールしないことは、どの組み合わせでも守る

### UIプレビューの作り方

- 題材ごとの部品（カフェのメニューなど）は、HTMLとCSSで描く。画像は使わない
- 部品のCSSは色・余白・角丸・影・フォントをすべてCSS変数で参照する。変数を差し替えるだけで見た目が変わるようにする
- 質問画面では、部品を囲む要素ごとにCSS変数を上書きして、AとBの違いを表現する

### 第2部のデモの作り方

第1部のプレビューが「見るだけの静止画」なのに対し、第2部のデモは「**触ると動くもの**」になる。作り方の決まりを分ける。

- 1問につき、A用とB用の2つのデモを作る。どちらも同じ題材・同じ文言にして、**部品の形と動きだけが違う**ようにする
- デモの中は触れるようにしてよい（押すとトーストが出る等）。第1部の「操作できる要素を置かない」という決まりは、第2部には当てはめない
- 動きの長さは `--duration` を参照する。K9（動きの速さ）の問題以外では、ニュートラル値（0.25秒）を使う
- `prefers-reduced-motion: reduce` の扱いは §4.2 に従う
- デモは結果ページの「定番UIキット」の見本としても使い回す。質問画面とは違うテーマ（その人のテーマ）で描かれても崩れないようにする

### 画面に出す文言

開発の知識がない同年代の友人が使うので、説明なしで意味が分かる言葉にする。

- 専門用語（UI・CSS変数・デザイントークン・プロンプトなど）は画面に出さない。出す場合は「何に使うものか」を一言添える
  - 例：AI向けプロンプト → 「AIに渡せる設計図」＋「ChatGPTなどに貼り付けると、あなた好みの見た目で画面を作ってくれます」
- **例外：UI部品の名前（トースト・モーダル・スケルトンスクリーンなど）は、あえて画面に出す。** 名前を知ってもらうことが目的のひとつなので、必ず一言の説明とセットで出す（§4.2）
- 16タイプは「お店」ではなく「場所」と呼ぶ（§1）
- 開発用のメモ（部品が仮である等）は本番の画面に出さず、`?debug=1` のときだけ表示する

### 診断サイト自体のデザイン

トップ・質問画面・ひと休み画面は、プレビューとデモの邪魔をしない控えめなデザイン（白〜薄いグレー、ゴシック体）にする。結果ページで一気にテーマが変わる落差を、演出として活かす。

## 6. データ構造

質問、タイプ、トークンはすべてTypeScriptの定数ファイルとして持つ。DBは使わない。

```ts
// src/data/types.ts（型定義）
export type AxisId = 'density' | 'decoration' | 'tone' | 'font';

export interface Question {
  id: string;              // 'q1'
  axis: AxisId;
  subject: string;         // 'cafe-menu'（どの部品を描くか）
  label: string;           // 'カフェのメニュー'
}

// 'left' / 'right' は「軸の左側・右側」の意味。画面上の位置ではない
export type AnswerValue = 'left' | 'right' | 'either';
export type Answers = Record<string, AnswerValue>; // { q1: 'right', q2: 'either', ... }

// 1問あたり 左=0 / どちらでもない=1 / 右=2 として合計した値（小数を避けるため2倍）
export type AxisPoints = 0 | 1 | 2 | 3 | 4 | 5 | 6;

export interface AxisScore {
  axis: AxisId;
  rightPoints: AxisPoints;
  rightRatio: number;      // 0〜1（rightPoints ÷ 6）
}

export interface TypeInfo {
  code: string;            // 'ARCG'
  shop: string;            // 'スマホの旗艦店'（§12）。画面では「場所」と呼ぶ
  quip: string;            // ひとことツッコミ
}
```

### 第2部（定番UIキット）のデータ

```ts
// src/data/kitTypes.ts
export type KitCategory = 'layout' | 'component' | 'motion';

// 'a' / 'b' は選択肢の識別子。画面上の位置ではない（第1部と同じく左右は入れ替える）
export type KitChoice = 'a' | 'b';
export type KitAnswerValue = KitChoice | 'either';
export type KitAnswers = Record<string, KitAnswerValue>; // { k1: 'a', k4: 'either', ... }

/** 選択肢ひとつ。名前と説明は画面にもAI向けの設計図にも出す */
export interface KitOption {
  id: string;              // 'toast'
  name: string;            // 'トースト'
  description: string;     // '画面の端に一瞬出て、自分で消える'
}

export interface KitQuestion {
  id: string;              // 'k4'
  category: KitCategory;
  label: string;           // 'お知らせの出し方'（画面に出す問い）
  a: KitOption;
  b: KitOption;
}
```

- 第2部の回答は `DiagnosisState` に持つが、`score.ts` には渡さない。**判定に混ざらないよう、型の段階で分けておく**
- 名前と説明は `kitQuestions.ts` の1か所にだけ書く。画面・見本・AI向けの設計図は、すべてここを参照する（文章にベタ書きしない）

### 軸とデザイントークンの対応

左右の値の間を、割合（rightRatio）で補間して実際の値を決める。


| 軸   | CSS変数                    | 左側の値         | 右側の値          |
| --- | ------------------------ | ------------ | ------------- |
| 情報量 | `--space-unit`           | 6px          | 16px          |
| 情報量 | `--font-size-base`       | 14px         | 17px          |
| 情報量 | `--line-height`          | 1.5          | 1.9           |
| 装飾  | `--shadow`               | なし           | 多層の柔らかい影      |
| 装飾  | `--surface-gradient`     | なし           | 2色のグラデーション    |
| 装飾  | `--border`               | 1px 実線       | なし            |
| トーン | `--color-primary` ほか配色一式 | 低彩度の寒色パレット   | 高彩度の暖色パレット    |
| トーン | `--radius`               | 4px          | 20px          |
| 見出し | `--font-family-heading`  | Noto Sans JP | Noto Serif JP |
| 見出し | `--font-family-body`     | Noto Sans JP | Noto Sans JP（変えない） |


※ 色や影は数値の補間が難しいため、割合が50%より大きいかどうかで左右どちらかのプリセットを使う（ちょうど50%は左側。タイプコードの判定と同じ境界・同じ比較にそろえる）。具体的な値は実装時に調整する。

`--font-family` は `--font-family-heading` と `--font-family-body` の2つに分ける（§4.1）。本文側は左右どちらでもゴシックのままなので、実質的に変わるのは見出しだけになる。部品のCSSは、見出しに当たる要素だけ `--font-family-heading` を参照する。

### 第2部が決めるCSS変数

第2部は配色や余白には触らない。**動きの長さと、どの部品を使うか**だけを決める。


| 問              | CSS変数 / 持ち方      | A        | B        | ニュートラル |
| -------------- | ---------------- | -------- | -------- | ------ |
| K9 動きの速さ       | `--duration`     | 0.15s    | 0.35s    | 0.25s  |
| K10 画面の切り替わり   | `--transition`   | `slide`  | `fade`   | `fade` |
| K1〜K8          | CSS変数ではなく、どの部品を描くかの選択として持つ | | | |


- `prefers-reduced-motion: reduce` のときは `--duration` を `0s` にする
- 第2部の値は第1部のテーマとは別に作り、結果ページで両方を適用する（混ぜると、どちらの軸が効いたのか分からなくなる）

## 7. 共有URLと、AIに渡せる設計図

### 共有URL（P1）

- 形式：`/?r=4026&k=abeabbaaba`
  - `r`：第1部。軸ごとの点数（2倍した値・0〜6）を、軸の順に並べた4桁の数字
  - `k`：第2部。K1〜K10の回答を順に並べた10文字（`a` / `b` / `e`＝どっちでもいい）
- タイプコードと割合は `r` の4桁から再計算できるので、URLにはこれだけ入れる
- `r` は各桁が0〜6の4桁でなければ無視してトップを表示する（不正な値への対策）
- `k` は `a` / `b` / `e` だけからなる10文字でなければ、**第2部だけを無かったことにして**第1部の結果を表示する（`r` が正しければ結果は出せるため、全部捨てない）
- `k` が無いURL（方針見直し前に共有されたもの）も、第1部だけの結果として表示する
- 共有URLから開いた場合は「友達の結果」と表示し、「自分も診断する」ボタンを目立たせる
- シェアには Web Share API を使い、使えない環境ではURLをコピーする

### AIに渡せる設計図（P0）

テンプレートに、第1部の軸の結果・トークンと、**第2部で選んだ部品**を埋め込んで、ブラウザ内で生成する。AIのAPIは使わない。

画面上では「AIに渡せる設計図」と呼ぶ（「プロンプト」は専門用語なので出さない。§5）。

```markdown
以下のデザイン方針でUIを作成してください。

## デザインタイプ：ARCG（スマホの旗艦店）
- 情報量：ややユッタリ（67%）。余白を広く取り、1画面の情報は少なめにする
- 装飾：はっきりリッチ（100%）。やわらかい影とグラデーションで、面に立体感を出す
- トーン：ややクール（67%）。彩度の低い寒色系でまとめる。角丸は控えめにする
- 見出し：はっきり明朝（100%）。見出しだけ明朝体（Noto Serif JP）にし、本文はゴシック体（Noto Sans JP）にする

## デザイントークン（CSS変数）
:root {
  --color-primary: #3B5B7A;
  --space-unit: 12px;
  --radius: 6px;
  --font-family-heading: 'Noto Serif JP', serif;
  --font-family-body: 'Noto Sans JP', sans-serif;
  --duration: 0.15s;
  /* ... */
}

## 使いたいUI部品・動き
- メニュー：ボトムナビ（画面の下にいつも並んでいる、行き先のボタン）
- 一覧：カード（1件を四角い面で見せる）
- 続きの見せ方：「もっと見る」ボタン
- お知らせ：トースト（画面の端に一瞬出て、自分で消える）
- 確認・選択パネル：ボトムシート（画面の下からせり上がってくる板）
- 読み込み中：スケルトンスクリーン（中身の形を先に灰色で出して待たせる）
- 切り替え：タブ
- 入力ミス：入力欄のすぐ下に、打った直後に出す
- 動きの速さ：きびきび（0.15秒ほどで終わる）
- 画面の切り替わり：フェード

## 守ってほしいこと
- 上記のトークン以外の色・フォントを追加しない
- 上記以外のUI部品を使う場合は、同じ役割の部品を2種類混ぜない
- アクセシビリティ（コントラスト比、タップ領域44px以上）は好みより優先する
- `prefers-reduced-motion` のときはアニメーションを無効にする
```

#### 「使いたいUI部品・動き」の作り方

- 名前と説明は `kitQuestions.ts` を参照して組み立てる（文章にベタ書きしない）
- 「どっちでもいい」を選んだ項目は、**行ごと書かない**（§4.2）。10問すべてが「どっちでもいい」なら、このセクションごと出さない
- 「同じ役割の部品を2種類混ぜない」の一文を必ず入れる。これが「一貫して使える自分の定番」という第2部の趣旨そのものなので

- 軸ごとに、寄り方の強さで文言を変える（「どっちも同じに見える」の追加で割合が7段階になったため、次の3段階にする）


| 割合（50%からの差）     | 文言        |
| ---------------- | --------- |
| 100% / 83%（33以上） | はっきり〜     |
| 67%（17）          | やや〜       |
| 50%（0）           | どちらでもない   |


- 「守ってほしいこと」に、好みよりも使いやすさを優先する一文を必ず入れる（UXの観点から突っ込まれないようにするため）
- 軸の表示名は `axes.ts` を参照して組み立てる（文章にベタ書きしない）
- 見出しの軸の文言は、本文がゴシックのままであることが伝わるように書く（§4.1）

```text
│   └── shops-src/          # 写真の元データ（PNG）。デプロイには含めない
├── public/
│   ├── images/
│   │   └── shops/          # 結果ページの写真（DFCG.webp 〜 ARPM.webp）
│   └── api/                # フェーズ2のみ（submit.php, stats.php）
└── dist/                   # ビルド結果。これをサーバーにアップロードする
```

- `vite.config.ts` の `base: './'` が重要。これがないと、サーバーのサブフォルダに置いたときにJSやCSSのパスが壊れる
- `public/` に置いたファイルは、ビルド時にそのまま `dist/` にコピーされる
