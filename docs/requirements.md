# UIタイプ診断 要件定義書

2026年10月20日 · @南保俊輔

## 1. 概要

2択のUI比較に12問答えるだけで、自分が好むUIのタイプ（16タイプ）がわかり、そのUIで再現された結果ページと、AIにそのまま渡せるデザインプロンプトが手に入るWebサービス。


| 項目      | 内容                                                        |
| ------- | --------------------------------------------------------- |
| 仮タイトル   | UIタイプ診断（「MBTI」は商標のため名称に使わない）                              |
| 目的      | UIの好みは人によって違うことを体験してもらう。自分の好みを言語化し、AIでのUI制作に使える形で持ち帰ってもらう |
| ユーザー    | 同年代の友人・先輩・後輩（主にスマホ）。評価者として先生も閲覧する                         |
| 解決したい課題 | 好きなUIを言葉で説明できない／AIにデザインを頼むとありきたりなUIになる                    |
| 位置づけ    | エンタメ診断。科学的な根拠はないことを明記する                                   |
| 課題      | 専門デプロイメントコースⅢ 中間課題（個人）。締切 2026-10-29 0:00（実質 10/28 中）     |


## 2. 前提条件

本体は静的ファイル（HTML/CSS/JS）だけで完結させる。サーバー側の処理は、フェーズ2の分布表示にだけ使う。

## 4. 診断ロジック

4つの軸を3問ずつ測り、多く選んだ側の文字を並べて4文字のタイプコード（例：`ARCG`）にする。1つの軸が3問なので、引き分けは起きない。

### 4つの軸


| 順   | 軸   | 左側（文字）         | 右側（文字）       |
| --- | --- | -------------- | ------------ |
| 1   | 情報量 | ギッシリ Dense（D）  | ユッタリ Airy（A） |
| 2   | 装飾  | フラット Flat（F）   | リッチ Rich（R）  |
| 3   | トーン | クール Cool（C）    | ポップ Pop（P）   |
| 4   | 文字  | ゴシック Gothic（G） | 明朝 Mincho（M） |


### 質問設計の原則

- 比べる2つのUIは、**測る軸だけが違い、他の3軸はニュートラル値で同じ**にする（視力検査方式）
- 問題ごとに題材を変え、場面が偏らないようにする
- 同じ軸の問題が連続しないよう、軸1→2→3→4の順で3周させる
- 選択肢A/Bの左右は問題ごとにランダムに入れ替え、位置による偏りを防ぐ
- 質問文は全問共通で「どっちが好き？」。軸の名前は回答中には見せない（先入観を防ぐ）


| 問   | 軸   | 題材         |
| --- | --- | ---------- |
| Q1  | 情報量 | カフェのメニュー   |
| Q2  | 装飾  | 音楽プレイヤー    |
| Q3  | トーン | 天気アプリ      |
| Q4  | 文字  | ニュース記事の見出し |
| Q5  | 情報量 | ECの商品カード   |
| Q6  | 装飾  | ログイン画面     |
| Q7  | トーン | ToDoリスト    |
| Q8  | 文字  | プロフィールカード  |
| Q9  | 情報量 | 大学の時間割     |
| Q10 | 装飾  | 通知一覧       |
| Q11 | トーン | SNSの投稿     |
| Q12 | 文字  | イベント告知     |


### 回答の選択肢

2つのUIの差が分からない人に無理やり選ばせると回答が実質ランダムになり、判定が濁る。そのため2択の下に「どっちも同じに見える」を小さく置く（2択と同じ大きさのボタンにはしない）。


| 回答           | 右側に寄せる点数 |
| ------------ | -------- |
| 左側を選ぶ        | 0        |
| どっちも同じに見える   | 0.5      |
| 右側を選ぶ        | 1        |


### 判定と割合

- 各軸の3問について、上の点数を合計する（0〜3）
- 小数を避けるため、内部では**合計を2倍した整数**（0〜6）で持つ
- 右側の割合 = 合計 ÷ 3 ＝ 2倍した値 ÷ 6（0% / 17% / 33% / 50% / 67% / 83% / 100%）。左側の割合 = 100% − 右側
- 割合が **50%より大きければ**右側の文字、**50%以下なら**左側の文字をタイプコードに使う（ちょうど50%は左側）
- 割合はデザイントークンの値の決定にも使う（同じタイプでも少しずつ違うUIになる）
- **テーマのプリセット切り替えも、タイプコードとまったく同じ境界・同じ比較を使う。** 片方だけ「50%以上」にすると、ちょうど50%のときにタイプコードと見た目が食い違う
- 16タイプそれぞれに、呼び名（§12）と解説文を用意する


| 2倍した値 | 0  | 1   | 2   | 3   | 4   | 5   | 6    |
| ----- | -- | --- | --- | --- | --- | --- | ---- |
| 右側の割合 | 0% | 17% | 33% | 50% | 67% | 83% | 100% |
| 使う文字  | 左側 | 左側  | 左側  | 左側  | 右側  | 右側  | 右側   |


## 5. 画面構成とUI

1枚のHTMLの中で画面を切り替えるSPA（シングルページアプリケーション）構成にする。ページを読み直さないので、回答の状態を保ちやすい。

**ui-craftというskill使いながら進める**

1. **トップ**：サービス名、ひとこと説明、「約2分・12問」、エンタメであることの注記、開始ボタン
2. **質問**（×12）：進捗バー（例：5/12）、「どっちが好き？」、2つのUIプレビュー（スマホでは上下に並べ、PCでは左右に並べる）、戻るボタン。タップしたら次の問題へ進む
3. **結果**：ページ全体が、そのタイプのテーマ（CSS変数）に切り替わる。上から順に以下を並べる
   1. タイプコードと呼び名
   2. 4軸の割合バー
   3. 解説文（好むUIの特徴を3〜4行）
   4. あなた専用UIのプレビュー（質問で使った部品のうち3つを、その人の値で再描画）
   5. AI向けプロンプト（コピーボタン付き）
   6. デザイントークン（P1・コピーボタン付き）
   7. 結果をシェア（P1）、もう一度診断する
4. **タイプ一覧**（P2）：16タイプのカードを並べる

### UIプレビューの作り方

- 題材ごとの部品（カフェのメニューなど）は、HTMLとCSSで描く。画像は使わない
- 部品のCSSは色・余白・角丸・影・フォントをすべてCSS変数で参照する。変数を差し替えるだけで見た目が変わるようにする
- 質問画面では、部品を囲む要素ごとにCSS変数を上書きして、AとBの違いを表現する

### 診断サイト自体のデザイン

トップと質問画面は、プレビューの邪魔をしない控えめなデザイン（白〜薄いグレー、ゴシック体）にする。結果ページで一気にテーマが変わる落差を、演出として活かす。

## 6. データ構造

質問、タイプ、トークンはすべてTypeScriptの定数ファイルとして持つ。DBは使わない。

```ts
// src/data/types.ts（型定義）
export type AxisId = 'density' | 'decoration' | 'tone' | 'font';

export interface Question {
  id: string;              // 'q1'
  axis: AxisId;
  subject: string;         // 'cafe-menu'（どの部品を描くか）
  label: string;           // 'カフェのメニュー'
}

// 'left' / 'right' は「軸の左側・右側」の意味。画面上の位置ではない
export type AnswerValue = 'left' | 'right' | 'either';
export type Answers = Record<string, AnswerValue>; // { q1: 'right', q2: 'either', ... }

// 1問あたり 左=0 / どちらでもない=1 / 右=2 として合計した値（小数を避けるため2倍）
export type AxisPoints = 0 | 1 | 2 | 3 | 4 | 5 | 6;

export interface AxisScore {
  axis: AxisId;
  rightPoints: AxisPoints;
  rightRatio: number;      // 0〜1（rightPoints ÷ 6）
}

export interface TypeInfo {
  code: string;            // 'ARCG'
  name: string;            // '静寂のミニマリスト'
  description: string;
}
```

### 軸とデザイントークンの対応

左右の値の間を、割合（rightRatio）で補間して実際の値を決める。


| 軸   | CSS変数                    | 左側の値         | 右側の値          |
| --- | ------------------------ | ------------ | ------------- |
| 情報量 | `--space-unit`           | 6px          | 16px          |
| 情報量 | `--font-size-base`       | 14px         | 17px          |
| 情報量 | `--line-height`          | 1.5          | 1.9           |
| 装飾  | `--shadow`               | なし           | 多層の柔らかい影      |
| 装飾  | `--surface-gradient`     | なし           | 2色のグラデーション    |
| 装飾  | `--border`               | 1px 実線       | なし            |
| トーン | `--color-primary` ほか配色一式 | 低彩度の寒色パレット   | 高彩度の暖色パレット    |
| トーン | `--radius`               | 4px          | 20px          |
| 文字  | `--font-family`          | Noto Sans JP | Noto Serif JP |


※ 色や影は数値の補間が難しいため、割合が50%より大きいかどうかで左右どちらかのプリセットを使う（ちょうど50%は左側。タイプコードの判定と同じ境界・同じ比較にそろえる）。具体的な値は実装時に調整する。

## 7. 共有URLとAIプロンプト生成

### 共有URL（P1）

- 形式：`/?r=4026`（軸ごとの点数（2倍した値・0〜6）を、軸の順に並べた4桁の数字）
- タイプコードと割合はこの4桁から再計算できるので、URLにはこれだけ入れる
- 各桁が0〜6の4桁でなければ無視してトップを表示する（不正な値への対策）
- 共有URLから開いた場合は「友達の結果」と表示し、「自分も診断する」ボタンを目立たせる
- シェアには Web Share API を使い、使えない環境ではURLをコピーする

### AI向けプロンプト（P0）

テンプレートに軸の結果とトークンを埋め込んで、ブラウザ内で生成する。AIのAPIは使わない。

```markdown
以下のデザイン方針でUIを作成してください。

## デザインタイプ：ARCG（静寂のミニマリスト）
- 情報量：ユッタリ（67%）。余白を広く取り、1画面の情報は少なめにする
- 装飾：フラット（100%）。影やグラデーションは使わず、境界は余白と細い線で表現する
- トーン：クール（67%）。彩度の低い寒色系。角丸は控えめ（6px程度）
- 文字：ゴシック（100%）。Noto Sans JP、本文16px、行間1.8

## デザイントークン（CSS変数）
:root {
  --color-primary: #3B5B7A;
  --space-unit: 12px;
  --radius: 6px;
  /* ... */
}

## 守ってほしいこと
- 上記のトークン以外の色・フォントを追加しない
- アクセシビリティ（コントラスト比、タップ領域44px以上）は好みより優先する
```

- 軸ごとに「割合が100%」「67%」「33%」「0%」の4段階で文言を変える
- 「守ってほしいこと」に、好みよりも使いやすさを優先する一文を必ず入れる（UXの観点から突っ込まれないようにするため）

## 8. 分布表示（フェーズ2・P2）

MVPが完成してから着手する。サーバーの準備ができなければ、作らずに提出する。

### 事前に確認すること（SSHで接続して確認）

- 以前作ったDBは PostgreSQL か SQLite か
- PostgreSQLの場合：接続情報（ホスト・DB名・ユーザー）を使って良いか
- SQLiteの場合：Webサーバー（PHP）が書き込めるフォルダを作れるか。DBファイルは**公開フォルダの外**に置く（URLで直接ダウンロードされないようにするため）
- 判断に迷ったら先生に確認する（権限の変更はセキュリティに関わるため）

### API


| メソッド | パス               | 入力                  | 出力                                      |
| ---- | ---------------- | ------------------- | --------------------------------------- |
| POST | `api/submit.php` | JSON `{"r":"4026"}` | `{"ok":true}`                           |
| GET  | `api/stats.php`  | なし                  | `{"total":120,"types":{"ARCG":14,...}}` |


### テーブル

```sql
CREATE TABLE results (
  id         INTEGER PRIMARY KEY,   -- PostgreSQLなら SERIAL
  type_code  TEXT NOT NULL,         -- 'ARCG'
  counts     TEXT NOT NULL,         -- '4026'
  created_at TEXT NOT NULL
);
```

- 個人を特定できる情報（IPアドレスなど）は保存しない
- 入力値はサーバー側でも4桁（各桁0〜6）の形式をチェックし、プリペアドステートメントで保存する
- 同じ人が何度も送信しないよう、ブラウザの localStorage に送信済みの印を残す（完全には防げないが、エンタメ用途なので許容する）
- 結果ページに「あなたのタイプは全体の◯%」と表示する

## 9. フォルダ構成

「データ」「ロジック」「表示」を分ける。ロジックは画面に依存しない純粋な関数にして、テストしやすくする。

```text
ui-type-shindan/
├── index.html
├── package.json
├── tsconfig.json
├── vite.config.ts          # base: './'（サブフォルダに置いても動くようにする）
├── src/
│   ├── main.ts             # 起動、画面の切り替え
│   ├── state.ts            # 回答の状態（現在の問題番号、回答）
│   ├── data/
│   │   ├── types.ts        # 型定義
│   │   ├── questions.ts    # 12問の定義
│   │   ├── typeInfos.ts    # 16タイプの呼び名と解説
│   │   └── tokens.ts       # 軸ごとの左右の値、プリセット
│   ├── logic/
│   │   ├── score.ts        # 回答 → 軸スコア → タイプコード
│   │   ├── theme.ts        # 軸スコア → CSS変数
│   │   ├── prompt.ts       # AI向けプロンプト生成
│   │   └── shareUrl.ts     # 共有URLの作成と読み取り
│   ├── views/
│   │   ├── topView.ts
│   │   ├── questionView.ts
│   │   └── resultView.ts
│   ├── components/
│   │   └── previews/       # 題材ごとのUI部品（cafeMenu.ts など12個）
│   └── styles/
│       ├── base.css        # 診断サイト自体のスタイル
│       └── preview.css     # 部品のスタイル（CSS変数だけを参照）
├── public/
│   └── api/                # フェーズ2のみ（submit.php, stats.php）
└── dist/                   # ビルド結果。これをサーバーにアップロードする
```

- `vite.config.ts` の `base: './'` が重要。これがないと、サーバーのサブフォルダに置いたときにJSやCSSのパスが壊れる
- `public/` に置いたファイルは、ビルド時にそのまま `dist/` にコピーされる

## 10. 実装手順とClaude Codeへの指示方法

dev-partnerskill使って

この要件定義書をリポジトリの `docs/requirements.md` に置き、Claude Codeには**1ステップずつ**依頼する。一度に全部作らせると、確認しきれない量のコードが出てくる。

1. **環境構築**：Vite + TypeScript（vanilla）でプロジェクトを作成し、`base: './'` を設定する。`npm run build` が通るところまで
2. **ロジック**：`types.ts`・`questions.ts`・`score.ts` を作り、判定のテストを書く（全問左なら `DFCG`、全問右なら `ARPM`）
3. **テーマ**：`tokens.ts`・`theme.ts` を作り、軸スコアからCSS変数を生成する
4. **部品**：プレビュー部品を、まず3題材だけ作る。CSS変数を差し替えると見た目が変わることを確認する
5. **画面**：トップ → 質問 → 結果の流れを作る（この時点で通しで遊べる状態にする）
6. **部品の残り**：残り9題材の部品を作る
7. **結果ページ**：解説、プロンプト生成とコピーを作る。16タイプの文章を用意する
8. **P1**：共有URL、トークンのコピー
9. **仕上げ**：スマホ実機での確認、デザインの調整、デプロイ
10. **P2**：分布表示（余裕があれば）

## 11. リスク・未決事項・テスト観点

### リスクと対策


| リスク                   | 対策                                     |
| --------------------- | -------------------------------------- |
| 12題材の部品づくりに時間がかかる     | 1つの部品を2つの問題で使い回すことも許容する（最低6題材）         |
| AとBの差が分かりにくく、選びにくい    | 友人に試してもらい、差を大きくする。迷う問題は差し替える           |
| 16タイプの文章づくりが重い        | 4軸それぞれの説明文（8パターン）を組み合わせて生成し、呼び名だけ16個書く |
| 結果のテーマで文字が読みにくくなる     | 文字と背景のコントラスト比 4.5:1 以上を全パターンで確認する      |
